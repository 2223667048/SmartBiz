# 完整业务模块解读：从需求到代码（工单模块）

## 需求分析与边界
一个企业客户向 AI 提出了它暂时答不好的问题。系统应该允许客户**主动提交问题**，给出工单号，由管理者后续改变状态。不要假装已经接入真实人工客服、短信或消息通知。

领域规则：
- 每个工单属于一个 session；游客只能读取自己的工单；管理员可查看所有工单。
- 工单主题 3~100 字符，详情 5~2000 字符；过长或空字段拒绝。
- 状态只能是 `new` / `in_progress` / `resolved`。
- 不允许前端随意设置初始状态；新工单永远是 `new`。
- 对外写接口必需有会话 token，对管理接口必需有管理密钥。

## 代码分层
- 表：`app/tickets.py:init_ticket_schema()` 创建表、关联 Session、检查状态。
- Repository/Service：`create_ticket`, `list_my_tickets`, `list_all_tickets`, `set_ticket_status`。
- API：`app/main.py` 的 `/api/tickets` 及 `/api/admin/tickets` 路由。
- UI：`web/index.html` 的 `ticket-form`，`web/app.js` 的 fetch 与列表渲染。
- 安全：前端用 `textContent` 显示主题，不解析为 HTML；SQL 全部使用占位符参数化。
- 测试：`tests/test_api.py::test_tickets_isolation_and_status`。

## 一次创建工单的全链路
1. 用户填写主题和描述，浏览器读取 FormData。
2. 前端 `POST /api/tickets`，携带会话 token，而不是 Langflow API Key。
3. `require_session()` 从 SQLite 查 token SHA-256 值对应的 Session ID；未登录返回 401。
4. Pydantic `TicketIn` 校验输入，FastAPI 路由去掉首尾空格。
5. `tickets.create_ticket()` 生成 UUID，用带占位符 SQL 插入 `tickets` 表。
6. 返回 `ticket_id` 和 `new` 状态；浏览器请求 `GET /api/tickets` 只展示当前会话记录。
7. 管理员带 `X-Admin-Key` 调用 PATCH 接口转为 in_progress 或 resolved。

## 自己新增一个字段的练习
需求：工单要支持紧急度 `priority=low|normal|high`。
- 数据：为 tickets 表加 priority；对已建数据库写迁移，不能仅改 CREATE TABLE（已存在表不会重建）。
- 输入：在 `TicketIn` 添加 `Literal['low','normal','high']`，默认 normal。
- 服务：insert SQL 加 priority，并在 list 返回。
- UI：给表单增加 select 下拉选项。
- 测试：验证默认值、非法枚举 422、普通用户无法操纵其他工单的权限。

## 为什么不让 Agent 直接更新工单？
LLM 可能受错误输入、提示词注入影响，不能成为唯一授权决策者。正确做法是让 Agent **建议创建工单**或调用权限有限且记录审计的工具，最终由受控业务 API 校验参数和权限。
